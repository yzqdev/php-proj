# AI 中间产物管理规范

本规范约束 AI 在项目中进行开发、分析、构建、调试、迁移、代码生成等过程中产生的中间产物的存放与管理，是 AI 工作区的强制规定。

核心目标：**所有中间产物集中存放，禁止随意散落在项目根目录、源码目录、资源目录及其他无关位置。区分可复用资源和一次性临时文件，避免误删有价值的内容。**

本规范由 gen-skill 复制到项目 `.agents/docs/artifact_guide.md`。首次在项目中应用时，执行第四节的全面整理与第七节的验收；日常开发中持续遵守第一、二、三、五、六节的规则。

## 一、建立统一的中间产物目录

优先在当前项目根目录建立统一的中间产物目录：

```text
项目根目录/
├── .ai-workspace/
│   ├── extracted/       # 解压、克隆、提取的第三方源码及参考项目
│   ├── scripts/         # 可复用的辅助脚本
│   ├── temp/            # 一次性临时文件和短期中间产物
│   ├── reports/         # 分析报告、检查结果、差异报告
│   ├── cache/           # 可重新生成的缓存
│   └── README.md        # 中间产物管理说明
├── .gitignore
└── ...
```

以上结构作为推荐方案，应结合当前项目实际情况调整。

如果项目已经存在类似的工作区、中间产物或辅助工具目录，优先评估并复用现有结构，不要重复创建多个用途相同的目录。

对于多模块、多版本项目，优先使用整个工作区统一的中间产物目录，而不是在每个子模块中重复创建。

## 二、明确不同文件的存放规则

### 1. 解压和提取的源码

例如：

- 从 GitHub 下载或克隆的第三方项目。
- 为了查看实现方式而解压的源码包。
- 从 JAR、ZIP、RAR 等文件中提取的源码。
- Minecraft 模组反编译源码。
- 用于版本迁移、功能对照的参考项目。
- 从其他项目提取出来的参考实现。

统一存放在：

```text
.ai-workspace/extracted/
```

要求：

- 解压源码可能会在多个任务中重复使用，不能因为当前任务结束就删除。
- 保留必要的原始目录结构，避免破坏源码的可读性和引用关系。
- 对不同来源、版本的源码进行合理命名，避免相互覆盖。
- 尽可能保留来源信息，例如项目名称、Git 仓库地址、版本号、下载时间等。
- 同一份源码已经存在时，先检查能否复用，不要反复下载和解压。
- 如果需要更新源码，先确认旧版本是否仍然被其他任务使用，避免直接覆盖。
- 不要将这些参考源码误认为当前项目正式源码，不得随意移动到正式 src 目录。

### 2. 可复用辅助脚本

统一存放在：

```text
.ai-workspace/scripts/
```

例如：

- Node.js 脚本（.js、.mjs、.cjs）。
- Python 脚本（.py）。
- PowerShell 脚本（.ps1）。
- Java、Kotlin 等辅助工具。
- 用于批量修改、代码迁移、文件转换的脚本。
- 用于生成配置、资源、JSON、语言文件的脚本。
- 用于代码对比、版本同步、项目扫描的脚本。
- 用于重复性检查和验证的脚本。

要求：

- 判断脚本是否具有重复使用价值。
- 具有复用价值的脚本应长期保留在 `.ai-workspace/scripts/`。
- 为脚本设置清晰的名称，能够直接理解用途。
- 复杂脚本应提供必要的注释、参数说明和运行方式。
- 不要为了整理目录而破坏脚本的相对路径、依赖关系和执行方式。
- 如果多个任务需要同一功能，应优先复用现有脚本，而不是重复编写。
- 脚本如果依赖特定版本、路径或环境变量，应尽量通过参数配置，不要随意硬编码绝对路径。
- 不要把正式项目运行所需的脚本、构建脚本和正式工具错误地移动到中间产物目录。

### 3. 一次性临时脚本

一次性脚本是指只为当前任务临时编写、没有后续复用价值的辅助代码。

例如：

- 临时文件批量重命名脚本。
- 一次性 JSON 数据转换脚本。
- 临时文本处理脚本。
- 临时目录扫描脚本。
- 临时数据提取和格式转换脚本。
- 为某次任务临时生成的 Python、Node.js、PowerShell 脚本。

统一在：

```text
.ai-workspace/temp/
```

或其临时子目录中创建。

要求：

- 一次性脚本执行完成、结果确认并且不再需要后，必须删除。
- 不得将一次性脚本长期留在项目根目录、源码目录或正式工具目录。
- 不得因为脚本使用了 Python 或 Node.js 就默认它需要保留。
- 如果发现一次性脚本具有明显的后续复用价值，可以整理后迁移至 `.ai-workspace/scripts/`。
- 删除前检查是否有其他脚本、文档或任务依赖它。

**一次性脚本必须清理，可复用脚本必须保留。**

### 4. 分析报告与中间数据

统一存放在：

```text
.ai-workspace/reports/
.ai-workspace/temp/
```

例如：

- 代码扫描结果。
- API 对比结果。
- 版本差异报告。
- JSON 中间数据。
- 临时生成的清单。
- 构建分析记录。
- 迁移过程中的阶段性结果。
- 资源检查结果。

具有长期参考价值的报告可以保留在 `.ai-workspace/reports/`。

只用于当前任务的临时数据放入 `.ai-workspace/temp/`，任务结束后根据实际情况清理。

### 5. 缓存

统一存放在：

```text
.ai-workspace/cache/
```

缓存必须满足：

- 可以通过原始数据或正式工具重新生成。
- 不包含正式项目必须提交的资源。
- 不与正式构建输出混淆。
- 不随意缓存体积巨大的无用数据。
- 清理缓存不能影响正式项目功能。

## 三、检查并完善 .gitignore

这是应用本规范的必要工作，不得跳过。

必须检查当前项目根目录的 `.gitignore`：

1. 确认 `.ai-workspace/` 是否已经被 Git 忽略。
2. 如果没有，添加规则。
3. 如果已有相关规则，检查是否存在匹配范围不完整的问题。
4. 确认 `.ai-workspace/` 下的文件不会被意外提交。
5. 检查是否存在已经被 Git 跟踪的中间产物。

建议添加：

```gitignore
# AI workspace and intermediate artifacts
.ai-workspace/
```

注意：

- `.gitignore` 只能阻止尚未跟踪的文件被 Git 纳入版本控制。
- 如果中间产物已经被 Git 跟踪，仅添加忽略规则并不会使其停止跟踪。
- 对已跟踪文件，先检查其性质，再决定是否使用 `git rm --cached`。
- 不得直接批量取消跟踪，不得影响正式项目文件。
- 不得覆盖或删除项目原有的 `.gitignore` 规则。
- 不得为了忽略中间产物而使用过于宽泛的规则，例如直接忽略所有 `scripts/`、`*.py`、`*.js`。
- 最终通过 `git check-ignore` 验证中间产物目录确实被忽略。

如果项目存在多个 Git 仓库或嵌套 Git 仓库，需要分别检查对应的忽略规则，不能只检查最外层目录。

## 四、整理已经散落的中间产物（首次应用或定期执行）

对当前工作区进行一次全面扫描。

重点检查：

- 项目根目录。
- 各个子项目根目录。
- src、resources 等源码目录。
- build、gradle、scripts 等目录。
- AI 自动生成的临时目录。
- 下载、解压、反编译、转换过程中产生的文件。
- 随机命名的 `.js`、`.py`、`.ps1`、`.json`、`.txt` 等文件。
- 不属于正式项目的 ZIP、JAR、源码副本和临时文件夹。

对发现的文件进行分类：

| 分类 | 处理方式 |
|---|---|
| 可复用的第三方源码 | 移入 extracted，长期保留 |
| 可复用辅助脚本 | 移入 scripts，长期保留 |
| 一次性临时脚本 | 确认完成后删除 |
| 临时数据 | 移入 temp，适时清理 |
| 有价值的分析报告 | 移入 reports |
| 可重新生成的缓存 | 移入 cache |
| 正式项目源码和资源 | 保留原位 |
| 正式构建、运行配置 | 保留原位 |
| 用途不明确的文件 | 暂不删除，先调查 |

移动文件前必须检查：

- 是否存在相对路径依赖。
- 是否被其他脚本引用。
- 是否被 Gradle、Maven、Node.js、Python 等工具引用。
- 是否被 IDE 配置或构建流程引用。
- 是否属于正式项目资源。
- 是否已经被 Git 跟踪。
- 是否有其他任务仍然需要使用。

不能仅凭文件名、扩展名或所在目录判断文件是否为临时产物。

## 五、持续遵守的管理规范

中间产物目录建立后，后续所有开发任务都必须遵守统一规则：

1. 需要解压源码时，优先使用 `.ai-workspace/extracted/`。
2. 需要创建可复用脚本时，使用 `.ai-workspace/scripts/`。
3. 需要创建一次性脚本时，使用 `.ai-workspace/temp/`。
4. 需要保存分析报告时，使用 `.ai-workspace/reports/`。
5. 需要保存可重新生成的缓存时，使用 `.ai-workspace/cache/`。
6. 禁止随意在项目根目录、源码目录、桌面或其他无关位置创建中间产物。
7. 不要重复下载、解压或生成已经存在且可复用的资源。
8. 任务结束时检查是否存在遗留的一次性脚本和临时文件。
9. 清理前必须确认文件不再被使用。
10. 不得为了追求目录整洁而删除有价值的参考源码、可复用工具或必要数据。

在 `.ai-workspace/README.md` 中记录：

- 各目录的用途。
- 文件归类原则。
- 可复用资源的保留规则。
- 一次性文件的清理规则。
- 如何复用已有脚本和解压源码。
- 新增中间产物时应遵守的路径规范。

## 六、执行安全要求

- 不得删除正式源码、资源、配置或用户数据。
- 不得擅自修改业务逻辑。
- 不得随意修改构建系统和依赖配置。
- 不得覆盖已有的同名文件。
- 不得执行危险的批量删除命令。
- 不得使用 Git reset、clean、checkout 等方式进行清理或回滚。
- 不得为了整理目录而破坏现有项目结构。
- 对无法确认用途的文件，保留原位并记录原因。
- 如果移动文件可能影响现有工作流程，应优先保留并提出调整方案。

## 七、整理任务完成后的验收标准

执行第四节整理任务后，必须逐项验证：

1. 已建立统一的中间产物目录。
2. 已经存在的可复用解压源码得到妥善保留。
3. 可复用 Node.js、Python、PowerShell 等脚本已统一归档。
4. 一次性临时脚本已经清理。
5. 其他临时数据已经合理归档。
6. 正式源码、资源和构建配置没有受到破坏。
7. `.gitignore` 已正确忽略整个中间产物目录。
8. 使用 `git check-ignore` 验证忽略规则有效。
9. 已检查 Git 已跟踪文件，不存在忽略规则失效的误判。
10. 已生成 `.ai-workspace/README.md` 管理说明。

整理任务完成后输出整理报告，包含：

- 新建的目录结构。
- 移动的文件及原始路径。
- 保留的可复用源码。
- 保留的可复用脚本。
- 删除的一次性临时脚本。
- 暂时未处理的文件及原因。
- `.gitignore` 的修改内容。
- Git 忽略验证结果。
- 是否存在路径引用或依赖风险。
- 尚未解决的问题。

**最终原则：中间产物可以长期保留，但必须集中管理；可复用资源不轻易删除，一次性临时脚本完成使命后必须清理。目录整洁不能以牺牲项目完整性和后续复用能力为代价。**
